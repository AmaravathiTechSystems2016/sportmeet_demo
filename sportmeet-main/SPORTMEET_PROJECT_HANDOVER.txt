4. WHAT THIS PROJECT IS

SportMeet is intended to be a sports venue and event marketplace.

Main idea:
Users discover sports venues, view available courts, book time slots, join events, pay online, leave reviews, and manage their profile.

Venue owners can:
Register as venue owners, create/manage venues, manage courts, see venue bookings, create events, and track their own activity.

Admins can:
Manage users, venue owners, venues, sports, amenities, bookings, events, payments, reviews, discounts, branding, static content, and social login keys.

The discontinued project already has a strong foundation. It is not a simple landing page; it is closer to a marketplace/admin SaaS product with three roles:
1. Public/player user
2. Venue owner
3. Platform admin

8. KNOWN ISSUES / PENDING INTEGRATION

Database:
- Original project was configured for PostgreSQL, not MySQL.
- I added SQLite support for local development.
- masterdata.sql is a PostgreSQL dump and cannot be imported directly into SQLite.
- If we want production-quality continuation, PostgreSQL is the easiest path because the dump and original settings are PostgreSQL-oriented.
- MySQL can be added later, but migrations and JSON/date behavior should be tested carefully.

Python compatibility:
- The machine has Python 3.14.
- Old pins for Pillow, psycopg2-binary, and django-filter needed loosening so dependencies install and run on Python 3.14.

Migrations:
- Several old discount/account migrations contained PostgreSQL-only SQL such as DO $$ and ADD COLUMN IF NOT EXISTS.
- I converted them to SQLite-safe no-op/Python migrations for local use.
- Before production deployment, review these migrations against the real production DB history.

Old sample script:
- backend/add_sample_data.py is partly stale.
- It creates users/venues/courts but breaks on events because it refers to an old Event.venue field that no longer exists.
- Use backend/seed_demo_data.py for demo data instead.

Frontend warnings:
- The React app compiles, but there are many lint warnings for unused imports/variables.
- BookingDetailPage has a no-mixed-operators warning around a conditional expression.
- These are not blocking local demo startup, but should be cleaned before serious development.

Admin stats:
- Admin dashboard venue stats appear to count "active" venues, but Venue.status uses approved/pending/rejected/suspended.
- This can show active: 0 even when approved venues exist.
- Fix by mapping active to approved or renaming the stat.

Venue price filtering:
- Some venue filters/order fields reference base_price_per_hour, but the Venue model no longer has that field.
- Pricing now appears to live on Court.price_per_duration and VenuePricing.
- Fix venue price filter to aggregate from courts.

Payments:
- Stripe code exists but needs real/test Stripe keys.
- Current local data includes demo payment records only.
- PaymentIntent and confirm flows need full browser checkout testing with Stripe test keys.

Social login:
- Facebook and Google endpoints/pages exist.
- Needs valid OAuth app IDs/secrets and redirect URL configuration.
- Admin social keys page exists but needs end-to-end verification.

Maps/location:
- Mapbox dependency exists.
- REACT_APP_MAPBOX_TOKEN is still placeholder.
- Nearby search is simple math in SQL; production should use proper geospatial support if location is important.

Email:
- SMTP settings are placeholders.
- Password reset, booking confirmations, venue notifications, and event reminders are not fully productized.

Redis/Celery:
- Packages and settings exist.
- No local Redis server was started.
- Background jobs/reminders/report generation should be reviewed and either completed or removed until needed.

Static/media:
- Django warns that backend/static does not exist.
- Media works locally through Django DEBUG serving.
- Production needs proper static/media storage.

Invoices:
- There is an apps/invoices folder/model references in the repo, but it is not included in INSTALLED_APPS or main URLs.
- Treat invoices as pending/unintegrated.

Reports:
- Report endpoints and models exist, but need validation against real product requirements.
- Analytics are basic and should be aligned with admin dashboard needs.

Authorization:
- Admin and owner routes exist, but permissions should be audited endpoint by endpoint.
- Some endpoints use IsAuthenticated but then filter manually; we should harden object-level permissions.

Tests:
- There are a few backend test scripts, but no reliable full test suite was run.
- Add API tests for auth, booking conflict rules, venue CRUD permissions, event registration, payment confirmation, and discounts.

Security:
- SECRET_KEY and demo credentials are local/demo only.
- DEBUG=True locally.
- CORS is open in debug mode.
- Production needs environment-only secrets, locked CORS, secure cookies/headers, HTTPS, logging, backups, and rate limiting.
